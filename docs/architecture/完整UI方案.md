# 云笈仙田录 完整 UI 方案（分层 + 换肤 + 场景化）

## 0. 参考案例

参考：星露谷物语 的 游戏内 HUD + 菜单体系  
实现方式：常驻轻量 HUD + 功能页分离（背包/制造/地图），保持主界面清爽。  
适用性：适用  
本项目调整：保留常驻 HUD 最小集，将复杂信息放入二级页面或弹层。

参考：明日方舟 的 信息优先级与操作层级  
实现方式：主操作突出、次操作弱化、危险操作二次确认。  
适用性：部分适用  
本项目调整：地块破坏与覆盖类动作加入确认或短撤销窗口。

参考：Minecraft 的 资源包机制  
实现方式：资源覆盖 + 默认回退，未覆盖项自动回落。  
适用性：适用  
本项目调整：皮肤系统采用同样的覆盖链，保证皮肤不完整时仍可运行。

参考：Terraria 的 地块交互反馈  
实现方式：工具态提示 + 交互反馈即时可见。  
适用性：适用  
本项目调整：强调当前地块模式（A 自动拼接 / B 侵入融合 / C 硬边）的显式状态提示。

## 1. 目标与边界

### 1.1 目标
- 建立一套配置驱动 UI 体系：结构与交互不依赖硬编码布局。
- 支持场景化视觉：自然和谐、混乱邪恶、科技秩序。
- 支持运行时换肤：不重置游戏状态，仅更新视觉层。
- 保证像素风可读性：整数倍缩放、统一视觉 token。
- 所有带边框按钮统一采用像素风边框语言，避免圆角化与柔光化破坏整体风格。
- 所有页面以“当前整窗内容区”为统一设计基准，确保不同分辨率下布局比例稳定。

### 1.2 非目标
- 本方案不改变核心玩法规则。
- 本方案不规定具体美术产能，只定义接口和约束。

## 2. UI 总体分层

### 2.0 整窗基准约束（强制）
- 页面布局必须先定义整窗结构，再定义局部组件。
- 整窗结构至少包含主视觉区、主交互区、辅助信息区三类语义区域（可合并，不可缺失）。
- 任何组件定位必须可映射到整窗网格或整窗比例锚点，禁止孤立绝对定位。
- 窗口分辨率变化时，优先保持整窗层级与信息优先级，不得让局部组件挤压主操作区。
- 新页面评审必须包含“整窗基准检查”结果，未通过不得进入实现。

### 2.3 功能卡片边界与滚动约束（强制）
- 所有功能卡片必须完整处于窗口内容区内，禁止卡片外框越界。
- 卡片尺寸必须先服从整窗布局配额，再决定卡片内部排版，不得反向挤占整窗结构。
- 当卡片内容超出可用高度时，只允许卡片内部纵向滚动。
- 页面层与卡片层默认禁止横向滚动，避免出现水平滚动条。
- 卡片内容溢出不得遮挡主操作区；若信息量持续增长，应拆分为分页或分组卡片。

### 2.4 主体开放式页面约束（强制）
- 首页、主入口、世界总览等主体开放式页面，不得采用整体封闭卡片包裹主视觉与主操作区。
- 主体开放式页面应以整窗层次组织内容，优先使用开放留白与分区引导视线。
- 仅允许在开放式页面的次要信息区使用局部轻量信息块，不得喧宾夺主。
- 若页面目标是沉浸式入口体验，禁止将整窗压缩为单一居中大卡片。

### 2.1 四层结构
1. 常驻 HUD 层  
职责：核心状态、快捷栏、当前工具与模式提示。  
要求：永远轻量，禁止堆叠次级信息。

2. 页面层  
职责：背包、建造面板、设置、地图、任务等完整页面。  
要求：一次只聚焦一个主任务。

3. 弹层层  
职责：确认框、掉落提示、错误提示、短时引导。  
要求：短生命周期，避免长期占据注意力。

4. 调试与开发层  
职责：调试开关、性能信息、资源检查。  
要求：与玩家 UI 隔离，可一键关闭。

### 2.2 渲染与输入边界
- 游戏世界渲染与 UI 渲染分离，互不污染状态。
- 输入先进入动作语义层，再路由到 UI 或世界交互。
- 同一时刻仅有一个焦点上下文：世界操作焦点或 UI 焦点。

## 3. 页面与信息架构

### 3.1 页面清单建议
- 主菜单
- 游戏内 HUD
- 背包与物品管理
- 建造与地块编辑
- 角色与成长
- 地图与目标
- 设置
- 暂停

### 3.2 导航规则
- 导航深度不超过 3 层。
- 每个页面必须有明确返回路径。
- 危险操作必须有确认或撤销。

### 3.3 信息优先级
- P0 常驻：生命、灵力、快捷栏、当前模式。
- P1 上下文：选中地块信息、可执行动作。
- P2 次级：日志、说明、扩展属性。

## 4. 交互规范（含地块系统）

### 4.1 三态交互反馈
- 输入反馈：按下即反馈（高亮、按压、音效）。
- 结果反馈：操作结果即时可见（地块变化、数值变化）。
- 恢复反馈：可撤销窗口或失败原因提示。

### 4.2 地块模式可见性
- 常驻显示当前模式：A 自动拼接 / B 侵入融合 / C 硬边。
- 切换模式时显示短时浮层，明确生效范围。
- 模式切换不应被页面跳转隐式重置。

### 4.3 工具态约束
- 工具与动作绑定清晰，例如采集、放置、破坏互斥。
- 破坏类操作默认带二次确认或短撤销（场景可配置）。

## 5. 换肤系统完整方案

### 5.1 设计原则
- 结构不变：页面结构与交互逻辑不因皮肤改变。
- 视觉可换：颜色、字体、贴图、阴影、装饰可替换。
- 稳定回退：皮肤缺失项自动回落到默认皮肤。

### 5.2 三层主题模型
1. 基础主题层（Base）  
定义全局默认 token。

2. 皮肤覆盖层（Skin）  
覆盖颜色、字体、贴图别名、组件状态样式。

3. 场景微调层（Scene）  
根据场景标签进行轻量偏移，如亮度、饱和度、描边强度。

最终样式值 = Base -> Skin -> Scene（后者覆盖前者）。

### 5.3 皮肤包组成
- 皮肤元信息：id、名称、版本、作者、适配比例、描述。
- token 文件：颜色、字号、间距、圆角、阴影、描边、动效。
- 资源映射表：语义资源名到实际贴图路径。
- 可选字体清单：标题字体、正文字体、数字字体。

### 5.4 资源回退链
- 当前皮肤资源
- 默认皮肤资源
- 内置保底资源

任一层缺失时自动回退，且记录日志用于皮肤质量检查。

### 5.5 运行时换肤流程
1. 用户选择皮肤。
2. 校验皮肤完整性与版本兼容。
3. 合并 Base + Skin + Scene token。
4. 通知 UI 层刷新样式与资源引用。
5. 保留页面状态与输入焦点，不重置 gameplay 状态。

### 5.6 场景与皮肤映射
- 自然和谐场景：默认映射柔和低对比皮肤，优先 A 自动拼接风格。
- 混乱邪恶场景：默认映射侵蚀感皮肤，优先 B 侵入融合风格。
- 科技秩序场景：默认映射高秩序皮肤，优先 C 硬边风格。

玩家可手动覆盖默认映射，保存为个人偏好。

## 6. 配置驱动规范

### 6.1 配置职责分离
- 页面配置：只定义结构、组件树、行为绑定。
- 主题配置：只定义 token，不放业务逻辑。
- 皮肤配置：只覆盖 token 与资源映射。

### 6.2 组件样式引用规则
- 组件只能引用语义 token，不允许直接写死颜色值与尺寸值。
- 同类组件必须共享状态 token：normal、hover、active、disabled。
- 所有带边框按钮必须使用像素风直角或像素切角轮廓，禁止圆角胶囊式边框。
- 边框按钮的描边宽度、边框色、背景色必须来自主题 token，保持整数像素清晰边缘。

### 6.4 卡片容器规范
- 卡片容器建议统一声明：`overflow-x: hidden`、`overflow-y: auto`。
- 页面根容器建议统一声明：`overflow-x: hidden`，防止任意子组件触发横向滚动。
- 卡片宽度由整窗网格列宽或整窗比例决定，禁止使用超出窗口的固定宽度值。
- 主体开放式页面不应默认套用整页封闭卡片容器；卡片仅用于局部信息承载。

### 6.3 动效规范
- 必需动效不超过 3 类：入场、状态切换、确认反馈。
- 所有动效支持全局降级开关（低性能设备可关闭）。

## 7. 分辨率与缩放策略

### 7.1 策略
- 采用逻辑分辨率 + 整数倍缩放。
- 缩放优先保证像素清晰，禁止非整数缩放导致模糊。

### 7.2 建议组合
- 16:9 逻辑分辨率优先：320x180、480x270。
- 5:3 逻辑分辨率可选：400x240。
- 详细对照见 [分辨率对照表.md](分辨率对照表.md)。

## 8. 性能与稳定性要求

### 8.1 性能要求
- UI 刷新应按脏区或状态变化驱动，避免全量重绘。
- 换肤流程应只刷新样式层与资源引用层。
- 高频数字更新采用节流策略。

### 8.2 稳定性要求
- 皮肤缺失资源不应导致崩溃。
- 页面配置错误需有降级提示页。
- 动效失败不应影响交互可用性。

## 9. 可用性与一致性要求

- 对比度达标，关键文案可读。
- 键鼠与手柄输入语义一致。
- 同一动作在不同页面反馈一致。
- 危险动作有明确确认或撤销。

## 10. 开发落地路线

### 阶段 1：基础框架
- 完成 UI 四层架构与状态路由。
- 完成 token 系统与基础主题。

### 阶段 2：核心页面
- 完成主菜单、HUD、暂停、设置。
- 完成地块模式显示与交互反馈。

### 阶段 3：换肤系统
- 完成皮肤包加载、覆盖、回退。
- 完成运行时换肤与持久化。

### 阶段 4：场景化
- 完成三类场景默认皮肤映射。
- 完成 A/B/C 过渡模式的视觉联动规范。

### 阶段 5：验收
- 性能、可用性、配置一致性、回退稳定性全量验证。

## 11. 验收清单

- 分层清晰：HUD、页面、弹层、调试层职责不混杂。
- 可配置：页面结构与样式均可通过配置变更。
- 可换肤：运行时换肤成功且不重置游戏状态。
- 可回退：皮肤缺失项自动回退且可记录。
- 可扩展：新增皮肤不需要修改业务逻辑。
- 可维护：token 与组件样式映射关系可追踪。

## 12. 风险与应对

- 风险：皮肤资源规模膨胀。  
应对：采用语义别名与差量覆盖，禁止全量复制资源。

- 风险：场景风格分裂导致不一致。  
应对：建立统一 token 基线，场景只做偏移不改骨架。

- 风险：换肤造成瞬时卡顿。  
应对：预加载关键资源，分帧刷新非关键区域。

- 风险：配置复杂度过高。  
应对：提供校验器与最小模板，强制字段检查。
